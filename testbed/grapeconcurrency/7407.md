Background: <https://issues.apache.org/jira/browse/GROOVY-7407>. Grengine has its own

with groovy-grape-ivy). Groovy 2.5.23 has no lock strategy. Groovy 6 alternatively has
groovy-grape-maven (`GrapeMaven`, Maven Resolver).

## 2. The tester: `GrapeConcurrency.java`

Java 8 syntax, compiled per cell by matrix.sh against the cell's Groovy (+ Ivy or
groovy-grape-ivy/-maven) classpath.

```
java [java-args] GrapeConcurrency -root DIR
     [-repo DIR [-http] [-httpDelay MS] [-httpFaults PERCENT]] [-lock]
     [-ivyTimeout SECS] [-threads N] [-timeout SECS]
```

* Starts 100 threads (default) that concurrently grab guava 10.0 … 19.0
  (10 threads per version) into an empty Grape cache (`-root DIR/grapes`), each into
  its own `GroovyClassLoader`, then load `com.google.common.base.Ascii` from it.
  Uses static `Grape.grab(Map, Map...)` like `@Grab`-generated code (fills in
  `autoDownload`, `disableChecksums=false`, `calleeDepth`).
* Uses the Groovy version's default Ivy config (`groovy/grape/defaultGrapeConfig.xml`
  or `groovy/grape/ivy/defaultGrapeConfig.xml`), written to `DIR/grapeConfig.xml` and
  set via `grape.config`, with: cache path redirected, `localm2` (~/.m2) removed;
  with `-repo` also jcenter removed and ibiblio root set to the local repo.
* Non-Ivy engine (GrapeMaven) with `-repo`: `repos` list cleared (via reflection)
  and only the local repo added – otherwise Maven Resolver still contacts Central
  (e.g. `PrefixesRemoteRepositoryFilterSource`), which hung in HTTPS reads.
* `-lock`: `Grengine.Grape.activate()` before the grabs.
* `-http`: serves the local repo itself via `com.sun.net.httpserver` on 127.0.0.1
  (free port, thread per request), instead of `file:` URLs.
* `-httpDelay MS`: sleeps before each response and after each 16 KB sent.
* `-httpFaults PERCENT`: that share of responses fails, equally as 503, connection
  closed after half of the body, or stalled after half of the body (until the end
  of the run). Counts printed as `HTTP faults injected: …`.
* `-ivyTimeout SECS`: adds an Ivy `<timeout-constraint>` (connection + read timeout)
  and sets it on all `<ibiblio>` resolvers (see section 6).
* After `-timeout` (default 60 s): still running threads are "hung"; they are
  grouped by stack (each distinct stack printed once, with count and example
  thread names), then failure messages with counts, leftover `.part` files, and
  `RESULT OK|FAILED <ok> ok, <failed> failed, <hung> hung (<secs>s)`.
* Exits with `Runtime.halt` (hung downloads could block shutdown hooks); a
  watchdog thread halts after timeout+60 s if the main thread itself hangs; an
  uncaught exception in main also halts (the HTTP server would keep the JVM alive).


## 3. matrix.sh options


  `3 runs (1 failed), 290 ok, 0 failed, 10 hung`.

Analysis of the logs:

* Ivy (Groovy 3+) without lock: no download errors any more (thanks to
  `artifact-lock-nio`), but hangs instead, almost always in **multiples of 10**,
  i.e. all threads of one guava version, waiting in
  `FileBasedLockStrategy.acquireLock` ← `ArtifactLockStrategy.lockArtifact` ←
  `DefaultRepositoryCacheManager.lockMetadataArtifact` (from `cacheModuleDescriptor`
  or `download`). Consistent with the user's 2025 findings.
* GrapeMaven without lock: never a clean run against Central.
* The 3 FAILED lock cells:
  * `java17-groovy4.0.33-lock` run 1: 1 ok, 99 hung, `guava-19.0.jar.part` left –
    one thread stuck mid-download, 99 waiting for the Grengine lock.
  * `java25-groovy6.0.0-maven-lock`: lock holder in `ServiceUnavailableRetryExec`
    → `Thread.sleep`, i.e. Central answered 503/429 and Maven Resolver was retrying
    with back-off – **throttling by Central**, at the very end of the matrix
    (also `java25 maven-nolock` run 3: only 2 ok). `java21 maven-lock` run 3 likely same.
  * (At that time only the first hung thread's stack was printed, which in lock mode
    is just a waiter → led to grouping by stack.)
* Timing: most matrix time went into the 60 s timeouts of hung runs; successful runs
  took 2–13 s (Groovy 2.5 with lock consistently ~12–13 s, Groovy 4+ ~6 s).
* Each run starts with an empty cache, and without lock up to 100 threads download
  the same files in parallel – thousands of requests over the whole matrix, which
  explains the throttling. So `--grape-central` only rarely.

## 5. Conclusions

* Grengine's Grape lock is **not obsolete**:
  * Groovy 2.5 has no Ivy lock strategy → massive failures without it.
  * Groovy 3+ Ivy: no errors any more, but hangs with real network conditions.
  * GrapeMaven (Groovy 6) without lock never clean against Central.
* The Grengine lock itself behaved correctly; its weak point is inherent to a
  global lock: one download that never returns blocks all grabs.
* Root cause of the hangs (most likely): **no Ivy connection/read timeouts in
  Groovy's default Grape config**, so a stalled transfer blocks forever; with
  `artifact-lock-nio`, all other threads needing the same artifact wait for it.


## 6. Possible suggestion to Groovy (and workaround already possible today)

Ivy ≥ 2.5.0 supports timeout constraints (`org.apache.ivy.core.settings.TimeoutConstraint`,
`NamedTimeoutConstraint`, `TimeoutConstrainedURLHandler`). Groovy 3+ ship Ivy 2.5.x.
`defaultGrapeConfig.xml` could get:

```xml
<ivysettings>
  <timeout-constraints>
    <timeout-constraint name="grape" connectionTimeout="30000" readTimeout="60000"/>
  </timeout-constraints>
  <settings defaultResolver="downloadGrapes"/>
  <caches lockStrategy="artifact-lock-nio"/>
  <resolvers>
    <chain name="downloadGrapes" returnFirst="true">
      ... (as in the default) ...
      <ibiblio name="localm2" timeoutConstraint="grape" ... m2compatible="true"/>
      <ibiblio name="ibiblio" timeoutConstraint="grape" m2compatible="true"/>
      ...
    </chain>
  </resolvers>
</ivysettings>
```

This can already be done manually: Grape reads `~/.groovy/grapeConfig.xml` (or the
file in system property `grape.config`) **instead of** the built-in default, so copy
the whole default and add the above (it replaces, it does not merge). The tester's
`-ivyTimeout` does exactly that.

Caveats:

* Ivy only; GrapeMaven (Groovy 6) uses Maven Resolver with its own timeout settings,
  which cannot be set from outside with Groovy 6.0.0 (see section 9).
* Does not fix Groovy 2.5's concurrency failures (no lock strategy).
* A stalled grab still blocks waiting threads until the timeout.
* Values 30 s / 60 s are just a proposal; tested only with 20 s.

## 9. GrapeMaven and Maven Resolver locking (follow-up, 30 Oct 2026)

Session with Claude Code (Opus 5.5), container (JDK 21, aarch64 Linux), Groovy 6.0.0
with groovy-grape-maven (Maven Resolver 2.0.23).

Question: would GrapeMaven work without the Grengine lock with
`-Daether.syncContext.named.factory=file-lock -Daether.syncContext.named.nameMapper=file-gav`?

* **The system properties have no effect.** Maven Resolver reads these settings
  only from the session config properties. GrapeMaven builds the session itself and
  only sets `java.version`, `java.home`, `os.detected.name`, `os.detected.arch` and
  two `aether.artifactDescriptor.*` properties, not the JVM system properties.
  Verified with `-Daether.syncContext.named.factory=bogus
  -Daether.syncContext.named.nameMapper=bogus`: no error, `RESULT OK` (if read,
  Resolver would fail with "Unknown NamedLockFactory name").
* **File locking is already the default** in Resolver 2.0.23: factory `file-lock`
  (`DefaultNamedLockFactorySelector.DEFAULT_FACTORY_NAME`), name mapper `file-gaecv`
  (`NamedLockFactoryAdapterFactoryImpl.DEFAULT_NAME_MAPPER_NAME`), i.e. per
  group/artifact/extension/classifier/version, finer than `file-gav`. The
  `grapesM2/.locks` directory is created during runs (lock files removed after
  release). So all `-maven-nolock` cells above already ran with file locking; the
  properties would only have switched to the coarser `file-gav` mapper.
* Local repo over HTTP, `-j 21 -g 6 --grape-runs 2`:

  ```
  --grape-http-delay 10:
  java21-groovy6.0.0-ivy-nolock      OK      200 ok, 0 failed, 0 hung
  java21-groovy6.0.0-ivy-lock        OK      200 ok, 0 failed, 0 hung
  java21-groovy6.0.0-maven-nolock    OK      200 ok, 0 failed, 0 hung
  java21-groovy6.0.0-maven-lock      OK      200 ok, 0 failed, 0 hung

  --grape-http-delay 10 --grape-http-faults 5:
  java21-groovy6.0.0-ivy-nolock      INFO    168 ok, 2 failed, 30 hung
  java21-groovy6.0.0-ivy-lock        FAILED  2 ok, 2 failed, 196 hung
  java21-groovy6.0.0-maven-nolock    INFO    176 ok, 14 failed, 10 hung
  java21-groovy6.0.0-maven-lock      FAILED  9 ok, 1 failed, 190 hung
  ```

  * maven-nolock with faults: all hung threads are in their own stalled socket read
    (`SessionInputBufferImpl.streamRead`), no other threads waiting for locks behind
    them (unlike Ivy). Failures ("Failed to read artifact descriptor", "Could not
    transfer") correspond to injected 503s/aborted transfers.
  * maven-lock: one stalled download blocks all grabs behind the Grengine lock, as
    with Ivy.
* Conclusion: the lock settings would not resolve the observed issues; as with Ivy,
  the cause is stalled transfers without effective timeouts. No matrix.sh option was
  added, since the properties have no effect with GrapeMaven 6.0.0.
* Possible suggestion to Groovy: let GrapeMaven pass system properties (or e.g.
  `grape.*`-prefixed ones) into the session config properties; that would make lock
  settings and transport timeouts (e.g. `aether.transport.http.requestTimeout`,
  `aether.transport.http.connectTimeout`) configurable.


## 10. GROOVY-12640: Ivy timeouts (follow-up, 1 Nov 2026)

Session with Claude Code (Opus 5.5), container (JDK 21, aarch64 Linux).

Filed <https://issues.apache.org/jira/browse/GROOVY-12640>, with the issue text in
`12640.md` and the minimal reproduction attached as `GrapeStall.groovy`.

* `GrapeStall.groovy` (`groovy GrapeStall.groovy [timeoutSecs]`): a local HTTP Maven
  repo on 127.0.0.1 serves the POM of `repro:stall:1.0`, then sends half of the jar and
  stalls. Ivy settings are like the default (`artifact-lock-nio`, one `ibiblio` resolver
  pointing at the local server). Two threads grab the artifact.
  * No timeout: both threads hang. One is stuck in a socket read (`MeteredStream.read`),
    the other in `FileBasedLockStrategy.acquireLock`.
  * `5` (timeout-constraint with 5 s connection and read timeouts): both fail with
    `Read timed out` and `download failed`, no hangs (~11 s).
  * Same results with Groovy 3.0.25 and 4.0.33 (Ivy 2.5.3), 5.1.3 (Ivy 2.6.0) and
    6.0.0 with groovy-grape-ivy (Ivy 2.6.0).
* Groovy 6.0.0 groovy-grape-ivy: `defaultGrapeConfig.xml` and `relaxedGrapeConfig.xml`
  still have no timeouts.
* Reported against Groovy 6; the issue says the same change would work for 4.0.x/5.x
  if a backport is wanted. GrapeMaven was left out (it has its own transport timeouts,
  see section 9).

### Is Grengine's Grape lock still needed with Ivy timeouts in place?

Yes. The timeouts fix the hangs, but not concurrency:

* Groovy 2.5 has no Ivy lock strategy at all (massive failures without the lock, section 4).
* `artifact-lock-nio` only protects the cache files. The single, JVM-wide `GrapeIvy`
  instance has shared state that nothing synchronizes (Groovy 6.0.0 source,
  `groovy/grape/ivy/GrapeIvy.groovy`; Groovy 5.1.3 `groovy/grape/GrapeIvy.groovy` has
  no synchronization either):
  * `loadedDeps`: a plain `WeakHashMap`, written to on every grab.
  * `grabRecordsForCurrDependencies`: one `LinkedHashSet` that each `grab()` clears and
    refills, so concurrent grabs overwrite each other's records (this matters most when
    a grab fails and the records are used for cleanup).
  * The shared `IvySettings` are changed on every call:
    `setDefaultResolver(autoDownload ? 'downloadGrapes' : 'cachedGrapes')`, and
    `ivy.checksums = ''` with `disableChecksums`, which is never reset. One grab's
    options can leak into concurrent ones.
  * The resolve ID is `caller#all-caller;working` plus the last 2 digits of the current
    millis. Its resolved files are deleted from the cache after the resolve, so
    concurrent grabs can share an ID and delete each other's files.
  * Our tests (identical grabs into separate class loaders) did not show visible
    failures from these, but they are race conditions in the code itself, not
    something tied to particular network conditions.
* Smoke test with faults and timeouts (section 4.4): without the lock 88 ok, 12 failed;
  with the lock 97 ok, 3 failed. That points the same way, but it is not conclusive
  with random faults.
* The lock and the timeout complement each other. The timeout bounds the lock's weak
  point: a stalled download now blocks the grabs waiting behind the lock only until it
  times out, not forever.

**PS:** I have added the following comment to
[[GROOVY-7407]](https://issues.apache.org/jira/browse/GROOVY-7407):

* Note that the Ivy lock strategy (artifact-lock-nio) only protects the Grape cache files.
  Concurrent grabs are still not safe, even with an Ivy timeout as proposed in
  [GROOVY-12640](https://issues.apache.org/jira/browse/GROOVY-12640):
  `GrapeIvy` has shared state that is not synchronized
  (e.g. `loadedDeps`, `grabRecordsForCurrDependencies`,
  and per-call changes to the shared `IvySettings`).
  So I still recommend wrapping the engine with one that locks,
  as Grengine's `Grengine.Grape.activate()` does.
  Details: [link to this 7407.md]
